Idea central

Mismo resultado esperado, distinto grado de control

El flujo completo debe entregar specs, planes, MRs, QA y deploy docs con formato consistente. Lo que cambia es cuánto puede adaptar cada dev el camino para llegar a ese resultado.

⚠️
Inmutable no significa terminado.

Algunos skills marcados como inmutables todavía necesitan refinamiento, pruebas y ajustes. La etiqueta define hacia dónde deben converger: un estándar común de Sky. Mientras maduran, pueden modificarse, pero esos cambios deberían elevar la calidad del core y mantener el contrato de salida del equipo.

Inmutable

Core estándar

Apunta a usarse como estándar común. Puede seguir evolucionando, pero sus cambios deben mejorar el core compartido y respetar reglas del cliente, formatos oficiales, criterios de QA o estructura de entrega.

  • Protege estándares de Sky, arquitectura, seguridad, releases y formatos de evidencia.
  • Los cambios deberían entrar por PR al repo central, con versión y changelog.
  • No se ajusta por preferencia personal si eso cambia el contrato de salida.
  • Puede modificarse mientras madura, pero para acercarse al estándar requerido, no para fragmentarlo.
  • Sirve para que dos devs generen artefactos comparables aunque trabajen distinto.

Gobernanza por dev

Override local

Parte de una base recomendada, pero el dev puede ajustar cómo se ejecuta: más manual, más automático, más corto o más exhaustivo.

  • Permite quitar pasos para ahorrar tokens si el dev los revisa manualmente.
  • Permite agregar chequeos, prompts, ejemplos o comandos según el repo y el contexto.
  • No debería romper el formato final ni saltear validaciones críticas.
  • Reconoce que la IA no es totalmente determinística y necesita feedback loops.

Qué hace cada skill y quién lo gobierna

La clasificación no mide importancia. Define si el comportamiento debe quedar fijo por estándar del equipo o si el dev puede adaptarlo sin cambiar el resultado final.

Inmutable

Qué hace

Convierte DOR, notas o conversaciones en una spec técnica con alcance, supuestos, flujos y criterios.

Por qué queda fijo

El formato de spec y los criterios mínimos deben ser comunes para todo el equipo.

Repo / SDK

Cómo podría verse instalado por cada persona

El dev consume un paquete estándar y mantiene un espacio local para overrides. Lo personalizable no modifica el core; lo propone como mejora si demuestra valor para todos.

Core versionado

Skills inmutables, formatos oficiales, templates, validaciones y reglas de cliente.

sky-ai-skills-core/ immutable/ templates/ validators/ changelog.md

Perfil del dev

Preferencias de ejecución, budgets, comandos locales, profundidad de QA y pasos manuales.

~/.sky-ai/ profile.yml overrides/ examples/ disabled-steps.yml

Contrato final

Los outputs pasan por validadores para asegurar que siguen siendo compatibles con el flujo del equipo.

outputs/ spec.md plan.md implementation.md results/summary.md deploy-doc.md
Criterio práctico

Cómo decidir si un skill se puede tocar

La pregunta no es si el dev puede hacerlo mejor o peor. La pregunta es si el cambio altera el contrato final del equipo.

Cambia formato finalDebe ir al core inmutable y pasar revisión del equipo.
Cambia solo el caminoPuede vivir como override del dev si mantiene la misma salida.
Ahorra tokensPermitido si el paso omitido queda manualmente cubierto y documentado.
Agrega controlPuede empezar local; si mejora consistencia, se promueve al core.
